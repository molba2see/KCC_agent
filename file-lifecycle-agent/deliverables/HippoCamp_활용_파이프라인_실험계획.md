# 구체화 v3 — 파일 정리 파이프라인·HippoCamp·실험·작업계획

기준일: 2026-11-02. 본 문서는 실행 설계이며, 아래 실험의 성능 결과를 아직 측정하지 않았다. 데이터 파일 목록·subset 주석 점검만 수행했다.

## 1. 서비스의 목표와 이번 결정

사용자는 평소처럼 여러 파일을 내려받는다. Agent는 기존 프로젝트·작업과 연결해 분류하고, 관련 파일을 함께 찾게 하며, 사용이 끝난 뒤 필요한 관계를 보존하면서 보관·정리를 돕는다. 행사 알림은 필수 타겟이 아니다. 과제·업무·연구·데이콘 프로젝트가 모두 사례가 될 수 있다.

HippoCamp는 ‘자료를 읽고 관련 파일과 근거를 찾아 연결하는 능력’의 평가에 활용한다. ‘어디로 옮길지·어떤 버전을 남길지·언제 완료인지·무엇을 정리해도 되는지’의 정답은 별도 시나리오로 만든다. 첫 버전은 학습·파인튜닝 대신 기존 모델과 명시적인 상태·정책을 연결한다.

## 2. 도식 읽는 법

제품 흐름: 허용 폴더/평가 원본 → 수집·식별 → 내용 읽기 → 기존 작업 후보 검색 → 파일 묶음·관계 → 근거·참조 검증 → 상태별 정리 계획 → 승인 정책에 따른 실행·복구.

평가 흐름: HippoCamp 원본은 Agent 입력, QA 정답·evidence·rationale는 채점기 전용이다. 정리·보존 시나리오 정답도 채점기 전용으로 둔다. Gold 파싱 텍스트는 원본 처리와 분리한 보조 조건에서만 제공한다.

파이프라인 그림의 파란색은 기존 로컬 모듈 재사용, 초록색은 이번 구체화에서 구현할 부분, 보라색은 HippoCamp 평가 자료, 빨간색은 모델 입력에서 차단할 정답 정보다. 도식은 설계도이지 전체 구현 완료 표시가 아니다.

## 3. HippoCamp 데이터는 무엇을 쓸 수 있나

공식 경로: [논문](https://arxiv.org/abs/2604.01221), [공식 코드](https://github.com/synvo-ai/HippoCamp), [데이터 카드](https://huggingface.co/datasets/MMMem-org/HippoCamp). PDF는 웹 도구의 크기 제한이 있어 기존에 받은 동일 버전 PDF와 [논문 HTML](https://arxiv.org/html/2604.01221v1)을 대조했다.

| 자료 | 사용할 곳 | 입력·정답 구분 |
|---|---|---|
| 원본 파일 트리 | 추출·검색·파일 연결 실험 | Agent에 허용된 프로필만 제공 |
| QA의 question | 관련 파일 탐색·답변 과제 | 추론 시 입력 가능 |
| answer·file_path 정답 집합·evidence·rationale·agent_cap | 파일 검색·근거 일치·실패 단계 채점 | 추론 입력·검색 인덱스에서 제외 |
| HippoCamp_Gold의 parsed segments | OCR/파서 영향을 분리하는 보조 실험 | Gold-text-assisted라고 따로 보고 |
| XLSX의 원래 경로·작성/수정 시각 | 허용 메타데이터·시간·구조 분석 | QAID·QANum 등 정답 연결 열은 제거 |
| 원본의 폴더 배치 | 기존 작업 구조 후보 또는 약한 참고 | 사용자의 유일한 최적 목적지 정답으로 간주하지 않음 |

공식 카드도 raw-only와 Gold/viewer 조건을 구분해 보고하도록 요구한다. 카드의 연구 라이선스는 비상업 연구·평가·교육을 허용하고, 원본 재배포와 허가 없는 범용/운영 모델 학습 등을 제한한다. 실험은 읽기 전용 원본과 로컬 작업 복사본으로 진행하고, 노션에는 통계·설계만 남긴다. [공식 배포·평가 경계·이용조건](https://huggingface.co/datasets/MMMem-org/HippoCamp/blob/main/README.md)

### 3.1 실제로 확인한 범위

데이터 revision: ff212ff7ec1a60d28023e65f7e7c4df5a87f552c. 공개 API 응답에서 private=false, gated=false를 확인했으며, 카드의 ‘gated 배포 의도’와 현재 접근 상태가 다르다. 이는 이용조건이 없다는 뜻이 아니다.

LICENSE·README·subset 주석 3개와 raw 파일 목록을 받았다. 전체 원본 약 42.4GB, Docker 이미지, 가중치 파일 자체는 받거나 실행하지 않았다. GitHub 공식 코드도 읽기용으로 확인했다. 공개 페이지의 전체 배포 크기와 논문의 원본 규모는 중복·파싱 자료 포함 범위가 다르므로 같은 숫자로 취급하지 않는다.

| 프로필 | subset QA 실제 점검 | PDF·PNG·JPG·JPEG 형식 후보 | 문서 추출기 확장 시 비음성·비영상 후보 |
|---|---:|---:|---:|
| Adam | 18 | 5 | 12 |
| Bei | 27 | 14 | 17 |
| Victoria | 11 | 0 | 2 |
| 합계 | 56 | 19 | 31 |

형식 후보는 주석의 file_type만으로 계산한 예비 필터다. 실제 원본을 읽고 근거가 추출되는지 검증하기 전에는 실행 가능 문항 수라고 부르지 않는다. 이 선택된 19문항 결과를 전체 581문항 점수와 비교하지 않는다.

fullset 581문항과 subset 56문항을 더한 637개는 독립 평가 샘플이 아니다. subset/fullset을 학습/테스트로 나누지 않는다. 질문 간 같은 근거 파일이 겹치므로 질문만 무작위 분할하면 누수가 생길 수 있다.

경로 점검에서 Adam·Bei subset은 주석 정답 경로가 목록과 맞았지만, Victoria subset은 정규화 후에도 5개 경로가 맞지 않는 1문항을 확인했다. 별칭·누락·배포 버전을 확인하고 해결 전에는 모델 오류로 채점하지 않는다. 근거 경로와 파일 수가 다르면 file_path 집합을 우선 검토한다.

### 3.2 데이콘·모델 파일 시나리오에도 쓸 수 있나

Bei fullset의 목록 875개 파일에서 .pth 5개, .pt 2개, .py 3개, .ipynb 8개를 확인했다. Diffusion/GPT 예제 하위의 가중치·노트북·코드가 존재한다. Bei subset에는 해당 가중치 파일이 없으므로 이 실험은 fullset의 필요한 작은 묶음을 별도로 골라야 한다.

활용 후보는 ‘코드·설정·체크포인트가 한 묶음인지’, ‘일부 이동이 경로 참조를 깨는지’, ‘최종 결과에 필요한 파일을 보존하는지’다. 공개 파일 목록만 확인했으므로 가중치가 실제로 재현 가능한지·어떤 것이 최고 성능인지 확인한 것은 아니다. 파일명 순서·수정 시각만으로 최종본을 단정하지 않는다. 원본 모델·노트북은 실행하지 않고 명시된 경로·매니페스트·해시부터 검사한다.

## 4. 단계별 구체 설계 — 입력·출력·근거·실험·작업

### S0. 데이터 경계와 실험 환경

입력: 허용된 로컬 폴더 또는 HippoCamp 한 프로필의 raw 파일. 출력: source_manifest, 읽기 전용 원본, 쓰기 가능한 sandbox, 별도 scorer 디렉터리.

처리: 프로필·revision·scope·모달리티를 고정한다. question만 추론으로 전달하고 answer/evidence/rationale/QAID는 별도 프로세스에 둔다. 원본 시각은 메타데이터로 읽고 다운로드 시각을 원래 사용 시각으로 오인하지 않는다.

근거: HippoCamp의 raw-only 평가 경계, 프로필별 접근 분리, Gold 조건 공개 요구. 현재 dataset 카드·주석·경로 점검을 완료했고 대량 원본 확보는 미완료다.

연결 실험: E0 데이터 적합성. 해야 할 작업 T01–T03. 완료 조건: 경로 매핑 오류·형식·라이선스·정답 노출 검사가 기록되고, 채점 정답 없이 추론 입력을 생성할 수 있음.

### S1. 수집·파일 식별

입력: 새 파일 이벤트·변경 이벤트. 출력: asset_id, 콘텐츠 해시, 현재/원래 경로, 출처, 감지 시각, 수집 상태.

처리: 파일 크기·수정 상태 안정화, 중복 이벤트 억제, 재시작 재스캔. 같은 바이트의 복사본과 새 버전을 구분한다. 경로가 변해도 같은 자료를 추적하도록 ID·콘텐츠 해시·경로 이력을 분리한다.

근거: organize의 중복/충돌 처리와 기존 로컬 실험의 재스캔·이동 테스트. HippoCamp 원본은 수집 모듈의 입력 사례가 될 수 있지만 실제 다운로드 완료 이벤트 정답은 제공하지 않는다.

연결 실험: E6 복사·이름 변경·부분 저장·재시작. 작업 T04. 완료 조건: 동일 복사본을 자료/알림으로 중복 등록하지 않고, 다른 버전을 잘못 삭제하지 않음.

### S2. 원문·메타데이터 추출

입력: 읽을 파일·형식. 출력: text_segments, 페이지/좌표/시각 locator, 원문 해시, 추출기 버전, 실패 사유.

처리: PDF 텍스트 우선, 이미지·스캔 PDF OCR, TXT/MD/CSV/JSON과 EML/ICS·DOCX 등은 필요 순서대로 추가한다. 읽을 수 없는 모델 가중치는 본문을 지어내지 않고 메타데이터·관련 코드의 명시적 참조로만 다룬다.

근거: 기존 macOS Vision·Poppler 경로, HippoCamp의 locator·Gold segments 인터페이스. Gold 원문을 쓰면 OCR까지 해결한 것처럼 보고하지 않는다.

연결 실험: E1 raw-vs-Gold와 파서 실패 분석. 작업 T05. 완료 조건: 지원/미지원 형식별 coverage·근거 위치 보존을 기록하고 실패 자료가 자동 이동으로 넘어가지 않음.

### S3. 기존 프로젝트·관련 자료 후보 검색

입력: 새 파일의 본문·파일명·허용 메타데이터, 기존 프로젝트 루트/README/승인 자료 또는 사용자 검색어. 출력: 후보 프로젝트·파일 top-k와 각각의 출처·점수.

처리: 파일명 검색→본문 BM25→필요 시 임베딩을 조합하고, 디렉터리·명시적 작업 ID·기존 연결을 재정렬에 활용한다. 시간 근접성은 보조 신호이며 유일한 귀속 근거가 아니다.

근거: LSFS 의미 인덱스, AI File Sorter 승인 예시 검색, HippoCamp의 구조·문맥 관련 오류 분석. 이 기술 각각을 최초 기능으로 주장하지 않는다.

연결 실험: E2 검색 기준선. 작업 T06. 완료 조건: 검색 파일 목록과 근거를 재현 가능하게 기록하며, 정답 QA 연결 열을 feature로 쓰지 않음.

### S4. 프로젝트 귀속·파일 묶음·관계 제안

입력: 후보와 실제 근거 구간. 출력: belongs_to / contains / exact_duplicate / version_candidate / referenced_by / produced_by 후보 및 근거·확인 상태.

처리: LLM은 스키마에 맞는 후보를 제안하고, 명시적 ID·파일 참조·ZIP 엔트리·매니페스트 같은 확인 가능한 근거와 단순 유사도를 구분한다. QA에 함께 필요한 파일이라고 모두 같은 프로젝트·버전이라고 라벨링하지 않는다.

근거: HippoCamp의 파일별 evidence는 ‘질문에 필요한 파일’ 정답이지 모든 관계 유형의 정답이 아니다. 관계 유형은 사람이 검수한 추가 라벨을 만든다. AI File Sorter와 Poly에 이미 개인화·애매한 이동 확인이 있어 질문 자체보다 묶음당 부담 감소를 검증한다.

연결 실험: E3 관계·귀속. 작업 T07–T08. 완료 조건: 잘못 합침/잘못 나눔과 질문 수를 함께 보고하며, 추정 관계를 확정된 참조로 저장하지 않음.

### S5. 원문·식별자·참조 검증

입력: 제안 관계·정리 후보. 출력: verified facts, 충돌·누락 목록, 실행 금지/확인 필요 조건.

처리: 인용이 원문에 있는지, 경로가 실재하는지, 작업 ID가 충돌하는지 검사한다. 이동 계획에서 필요한 참조 파일·외부 참조를 확인한다. 서로 다른 버전은 별개로 보존하며 ‘가장 최신 수정 시각=최종본’으로 정하지 않는다.

근거: HippoCamp의 경로 환각·개체 연결 오류, 기존 v2의 근거 검증·모호성 보류 테스트. 일반 프로젝트 참조 검증은 신규 구현이며 현재 완료된 것은 아니다.

연결 실험: E1/E3/E4. 작업 T09. 완료 조건: 허위 인용·없는 경로·충돌 식별자를 보류하며, 구조를 해석하지 못한 참조를 안전하다고 간주하지 않음.

### S6. 작업 상태·보관 정책 기반 계획

입력: 검증된 관계, 진행/중단/완료 사건, 보존 정책·유지 의사. 출력: plan_id, 처리 묶음, 허용 목적지, keep/archive/defer/link/move 후보, 이유와 사전 조건.

처리: 사용 중 자료·공유 참조는 유지한다. 사용자가 완료를 확인하면 보관 계획을 만든다. 같은 프로젝트 자료라도 최종본·증빙·원본·재생성 가능한 임시 산출물을 구분한다. atime·마감·경과 시간만으로 완료나 삭제 가능성을 확정하지 않는다.

근거: Finding and Reminding의 자료 상태 논의, 기존 도구의 대기·보류 기능. HippoCamp에는 완료/보존/목적지 정답이 없어 새 시나리오가 필요하다.

연결 실험: E5 연속 유입·완료·재개. 작업 T10. 완료 조건: 같은 파일도 상태·공유 참조에 따라 기대한 계획으로 바뀌고 유지·거절을 반복 질문하지 않음.

### S7. 확인·실행·복구

입력: 검증된 계획·사용자 사전 허용 범위. 출력: 실행 기록, 현재 경로, 실행 전후 해시·상태, undo 결과.

처리: 낮은 위험의 분류·가상 뷰는 허용 범위 안에서 자동화하고, 영향이 큰 이동·보관 전환은 묶음 단위로 확인한다. 실행 직전 파일·참조를 다시 확인한다. 첫 MVP는 영구 삭제를 제외한다. 이름 충돌은 덮어쓰지 않는다.

근거: organize 충돌 처리, AI File Sorter 복구, TheYellowDuck 저널, 기존 프로토타입의 실제 보관·되돌리기. 묶음 전체의 중단 복구·재실행 정합성은 추가 구현/검증 대상이다.

연결 실험: E4/E6. 작업 T11–T12. 완료 조건: 원본 바이트·필수 참조 유지, 충돌 시 무변경, 정의한 실패 지점에서 복구 가능. ‘모두 보류’로 오류만 낮추지 않도록 자동 처리율도 보고한다.

## 5. 해볼 만한 실험 — 우선순위·대조군·지표

### E0 · P0 · 데이터 적합성 및 누수 점검 — API 불필요

질문: 어떤 문항을 실제로 처리·채점할 수 있나? 자료: subset 주석 56개·원본 파일 목록. 비교: 주석 경로와 실제 상대 경로, 형식별 처리 가능성. 지표: 매핑 성공률, 미지원 형식, 추출 실패, 정답 노출 여부.

현재: 주석 56개·목록 점검 완료, PDF·일반 이미지 형식 후보 19개, Victoria 1문항 경로 이슈 확인. 다음: 필요한 원본만 받아 읽기 smoke test. 처리 가능한 것만 선택하면 그 선택 규칙과 제외 수를 함께 보고한다.

### E1 · P1 · 원문 추출 vs Gold 파싱 텍스트

질문: 실패가 OCR/파서 때문인가, 검색·판단 때문인가? 조건: 동일 질문·동일 검색/생성기로 raw 추출과 Gold segments 입력을 비교. Gold의 QAID/QANum·정답·rationale는 제거한다. 지표: locator coverage, 근거 파일 recall, 인용 검증 실패, 처리 시간. Gold 조건을 공식 raw-only 점수처럼 보고하지 않는다.

첫 규모 제안: 포맷 확인된 10~19문항. 모델 없이 추출 coverage부터 검사하고, 답변 비교는 API/로컬 모델을 정한 뒤 실행한다.

### E2 · P1 · 관련 파일 검색 기준선 — 첫 실행 권장

질문: 이름·본문·구조 정보가 얼마나 도움이 되나? 조건: R0 파일명/경로, R1 본문 BM25, R2 본문+임베딩, R3 R2+허용된 경로·작업 구조로 재정렬. 원본 내용·질문·top-k·예산을 맞춘다.

지표: file Recall@5/10, Precision@k, MRR, 전체 근거 집합 회수율, 시간·비용. 정답은 QA의 file_path 집합이며 질문의 답은 검색기에서 숨긴다. R0/R1은 유료 API 없이 실행 가능하다. 같은 파일을 공유하는 문항 묶음으로 개발·평가 분리를 검토한다.

### E3 · P1 · 관련 파일 묶음·프로젝트 귀속

질문: 비슷한 파일을 잘못 합치지 않고 필요한 묶음을 만들 수 있나? 자료: 실제 파일에서 30~50개 쌍/작은 묶음을 골라 사람이 belongs_to / referenced_by / version_candidate / unrelated를 검수한다. 후보 수량은 계획치다.

조건: 유사도만 / 본문 LLM / LLM+명시적 ID·경로 관계 검증. 지표: 관계별 pair precision/recall/F1, 잘못 합침률, 묶음당 확인 질문·수정 수. co-evidence는 후보 추출용 약한 신호이며 관계 정답으로 자동 변환하지 않는다.

### E4 · P1 · 정리 전후 작업·검색 유지

질문: 정리한 뒤에도 필요한 파일을 찾고 사용할 수 있나? HippoCamp 복사본에서 선택 파일을 임시 다운로드함으로 옮기는 파생 과제 20~30개를 만든다. 허용 목적지·keep·link도 사람이 정의한다. 원래 폴더가 항상 최적이라고 가정하지 않는다.

조건: 규칙 정리 / 파일별 내용 분류 / 프로젝트 문맥+묶음 계획. 같은 모델 조건의 자체 대조군과, 버전·모델을 고정한 기존 제품 비교를 분리한다. 지표: 허용 목적지 일치, 정리 후 QA 근거 회수, 참조 보존, 수정 횟수. 경로가 바뀐 뒤 채점은 stable asset ID↔path mapping으로 해 정답 경로 변화 자체를 모델 오류로 세지 않는다. 이 과제는 HippoCamp 기반 파생 실험이며 공식 정리 benchmark 점수가 아니다.

### E5 · P2 · 유입→완료→재개 라이프사이클

질문: 상태를 넣으면 사용자 부담과 보존 오류가 줄어드나? 직접 만든 10~20개 사건 시나리오에서 파일 유입, 동일/다른 버전, 프로젝트 완료, 다른 활성 프로젝트 참조, 재개를 순차 재생한다. 실제 다운로드 이력이라고 주장하지 않는다.

조건: C0 파일별 분류, C1 프로젝트 문맥, C2 관계 제약, C3 상태·보관 정책. 추출기·모델·자료·사건 순서는 동일하게 고정한다. 지표: 필요한 파일의 정리 제안률, 불필요 보존, 반복 질문, 수정·복구 시간, 자동 처리율. 삭제 금지와 사용자 유지 의사는 hard constraint로 둔다.

### E6 · P0/P2 · 견고성과 복구 — API 불필요

질문: 실제 파일 이벤트와 실행 실패에서 망가지지 않나? 복사본·동명 다른 파일·변경 중 파일·잘못된 출력 위치·대상 충돌·실행 중 재시작을 주입한다. 지표: 잘못 덮어쓰기/손실/중복 실행 수, undo byte match, DB↔파일 경로 일치, 처리 coverage.

기존 v2에서 확인한 단일 파일 이동·충돌·undo는 재사용하되, 새 묶음 계획·프로젝트 관계의 정합성을 별도 검증한다. 모든 상황을 ‘완전 안전’이라고 포장하지 않는다.

### E7 · P2 · 가중치·노트북 묶음 보호

질문: 모델 파일을 내용 분류로 흩뜨리지 않고 실제 코드 참조와 연결해 보존할 수 있나? Bei fullset의 관련 코드/노트북과 .pt/.pth 작은 묶음을 고르고 코드에 명시된 경로를 정적으로 검수한다. 파일을 로드하거나 학습·추론 실행하지 않는다.

조건: 확장자·파일명 분류 / 프로젝트 루트 전부 보호 / 확인된 참조 기반 묶음 계획. 지표: 참조 경로 보존, 안전하게 정리한 범위, 필요한 체크포인트를 잘못 정리한 비율. 어느 가중치가 최고 성능인지는 평가 로그·정답이 없으면 판단하지 않는다. 재현 실행까지 검증하려면 별도의 환경·권한·자원·정답이 필요하다.

## 7. 첫 실행 순서와 진행 판정

1. E0를 마무리하고 Adam·Bei subset에서 PDF/이미지 형식 후보의 필요한 원본을 소규모로 확보한다. 원본 판독이 되는지 검증한다. 현재 형식 후보는 19문항이며 추가 제외가 생길 수 있다.
2. E2의 R0/R1을 먼저 실행한다. 모델 성능보다 파일 목록·경로·채점 누수가 없는지 확인한다.
3. 같은 질문으로 E1 raw/Gold 조건을 비교하고, 근거를 찾은 뒤 틀린 경우를 분리한다.
4. E3/E4의 관계·목적지 추가 정답을 만들어 묶음 계획을 검증한다. 이때부터 제품 차별화 효과를 측정한다.
5. 파일 찾기/작업 유지가 확인되면 E5/E7로 상태와 모델 파일을 확장한다. 대량 원본·영상·음성·파인튜닝·다중 에이전트·전 디스크 감시는 첫 필수 범위에서 제외한다.

성공 주장은 ‘폴더가 예뻐졌다’가 아니라 동일 오류 수준에서 줄어든 확인·수정 시간과 필요한 파일·참조 보존으로 한다. 모두 보류하면 사고는 적어도 자동 정리의 가치가 없으므로 처리율도 함께 제시한다.
