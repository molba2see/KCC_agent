# 임시 자료 라이프사이클 관리 — 베이스라인 v0.1

설계일: 2026-11-02 · 설계 산출물이며 구현·성능 측정은 아직 수행하지 않음.

출처: [노션 「임시 자료 라이프사이클 관리」](https://www.notion.so/3f89082a41fc81f48cbfc06438fbf783). 원문의 1~12절을 확인해 범위를 정했다. 아래 처리 계약·평가 수량·개발 순서는 구현을 위한 제안이다.

**저장한 자료를 이해하고, 필요할 때 다시 보여주고, 사용이 끝난 뒤 정리까지 돕는다.** 첫 버전은 새 모델 학습 없이 하나의 구조화 추출 모델과 명시적인 상태·알림 규칙으로 만든다.

## 1. 첫 구현 범위

한 운영체제에서 실행하는 로컬 Python 프로그램. 허용된 다운로드·스크린샷 폴더 2개, PDF·이미지 40~50개, 자료 종류는 신청·행사 / 과제·참고 / 영수증·증빙 3종으로 제한한다. 북마크 가져오기·휴대폰 동기화는 후속 단계다.

사용자는 처음에 감시 폴더·보관 폴더·기본 알림 시점·유형별 보관 기준을 설정한다. 이후 평소대로 저장하고 중요한 모호성, 완료 여부, 이동 승인만 확인한다. 처음부터 원본을 옮기지 않고 자료 카드와 논리적 분류를 먼저 만든다.

## 2. 단계별 처리 계약

| 단계 | 입력 | 처리와 책임 | 출력 / 예외 처리 |
|---|---|---|---|
| 01 감지 | 허용 폴더의 새 파일·변경 | 코드: 다운로드 임시 확장자 제외, 크기·수정 시각 안정화 확인, 재시작 시 누락 스캔 | 처리 대기 항목. 아직 쓰는 파일은 재확인 |
| 02 식별 | 안정화된 파일 | 코드: SHA-256, 파일 형식·크기 확인 | 자료 ID·경로. 동일 바이트는 기존 자료에 경로 연결; 유사 버전은 별개 보존 |
| 03 읽기 | PDF / 이미지 | 코드·도구: PDF 텍스트 우선, 텍스트 부족 페이지와 이미지는 OCR | 페이지·텍스트·가능한 좌표·추출 상태. 실패는 검토함, 기한 추정 금지 |
| 04 이해 | 추출 텍스트·파일명 | LLM: 자료 종류, 주제, 목적 후보, 필요한 행동, 기한 후보, 근거를 JSON 추출 | 검증 가능한 추출 레코드. 근거 없는 필드는 null |
| 05 검증·연결 | 추출 결과 + 기존 자료 | 코드: 스키마·날짜 정규화·근거 존재 검사. 제목·주최자·행사일·식별자 등으로 묶음 후보 생성 | 같은 작업의 자료 묶음. 날짜 충돌·불확실한 병합은 사용자 확인 |
| 06 저장 | 검증된 필드·묶음·근거 | 코드: SQLite 트랜잭션, 자료 상태와 작업 상태 분리, 변경 이력 | 원본 경로·해시·묶음·기한·상태·추출 버전 |
| 07 계획·재사용 | 상태·기한·사용자 사건·검색어 | 코드가 알림 자격·예약·취소·정리 자격 결정. AI는 설명 문장 생성 | 자료 묶음 알림, 검색 결과, 확인 질문, 정리 제안 |
| 08 실행·복구 | 사용자의 보관 승인 | 코드: 대상 충돌 검사, 이동, 해시 검증, 이력 확정 | 보관 경로·되돌리기. 실패는 경로 재확인 후 복구·오류 표시 |

LLM은 의미와 후보를 추출한다. **상태 변경·예약·파일 이동은 코드가 검증 후 수행한다.** 외부 API는 사용자가 허용한 자료의 필요한 부분에만 적용하고, 미허용 자료는 로컬 추출·검토 경로에 둔다. 문서 안에 적힌 지시문은 추출 대상 텍스트로만 다룬다.

## 3. AI 출력의 최소 스키마

```json
{
  "category": "application_event",
  "title": "캠퍼스 아이디어 공모전",
  "purpose_candidate": "공모전 신청 참고",
  "action_candidate": "신청서 제출",
  "identifiers": {"organizer": "예시 기관", "event_date": null},
  "deadlines": [{
    "kind": "application_close",
    "raw": "2026년 11월 9일 18시까지 접수",
    "normalized": "2026-11-09T18:00:00+09:00",
    "evidence": {"page": 1, "quote": "2026년 11월 9일 18시까지 접수", "bbox": null}
  }],
  "needs_review": false,
  "review_reasons": []
}
```

예시는 합성 자료다. 날짜 종류를 행사일·접수 마감·쿠폰 만료로 구분한다. 연도·시간대·오전/오후가 불명확하면 확인 대상으로 남긴다. 자정 마감이나 현재 연도를 임의로 채우지 않는다. 저장 목적은 후보이며 실제 신청 의사나 완료 상태를 문서에서 만들어내지 않는다. 모델이 낸 신뢰도 숫자만으로 자동 실행하지 않고 근거·필수 필드·모순 검사 결과로 검토 여부를 정한다.

## 4. 상태와 다음 행동

자료 상태와 연결된 작업 상태를 분리한다. 같은 행사라도 안내문과 증빙의 보관 결정은 다르다.

| 현재 조건 / 사건 | 다음 행동 |
|---|---|
| 목적·날짜 불명확 | 미분류 또는 확인 대기. 확인 전 해당 자동 알림 보류 |
| 유효한 행동 기한 + 미완료 + 사용자의 알림 설정 허용 | 묶음 단위 알림 1개 예약. 알림 해제 가능 |
| 날짜만 있고 필요한 행동 없음 | 자동 알림 없음. 검색 가능한 자료로 보관 |
| 관련 작업 시작 / 사용자 검색 | 연결된 안내·양식·참고자료와 원문 근거 제시 |
| 파일 열기 | 사용 기록만 남김. 완료로 변경하지 않음 |
| 명시적 완료 | 작업 완료, 남은 행동 알림 취소. 안내문은 정리 검토, 증빙은 보관 기준 적용 |
| 미루기 | 사용자가 정한 시점으로 알림 갱신. 마감 뒤로 미루면 경고·확인 |
| 같은 행사 연장 공고 유입 | 공식성·행사 식별·변경 근거 확인 후 기한 버전 갱신, 이전 예약 취소·교체 |
| 변경 공고가 모순되거나 묶음 불확실 | 기존 기한을 묵시적으로 덮어쓰지 않고 확인 요청 |
| 기한 지남 | 유효성 재확인. 완료로 간주하거나 정리 대상으로 자동 확정하지 않음 |
| 정리 제안 거절 / 계속 보관 | 유지 의사와 보류 사유 저장. 같은 자료·같은 조건 제안 억제 |
| 보관 승인 | 이동·검증 후 보관 상태. 실행 이력으로 되돌리기 |

알림 식별 키는 `(user_id, bundle_id, action_kind, reminder_slot)`로 두고 deadline_version을 갱신한다. 스케줄러는 DB의 활성 버전을 재확인하며, 발송 기록으로 재시작 후 중복을 막는다. 정시 알림은 놓쳤을 때의 보충 발송 규칙도 둔다.

자료 상태: `미분류 → 사용 대기 → 진행 중 → 완료 → 정리 검토 → 보관`. 진행 중은 사용자의 작업 시작 사건으로 전환한다. 참고·증빙처럼 행동이 없는 자료는 정책에 따라 사용 대기 또는 보관으로 갈 수 있다. 정리 거절은 별도의 `keep` 플래그로 기록하고, 미루기는 작업·알림 속성으로 관리한다.

## 5. 저장 구조와 최소 구성

| 구성 | 첫 구현 선택 | 책임 |
|---|---|---|
| 로컬 수집기 | Python 폴더 감시 + 재시작 스캔 | 감지·안정화·해시 |
| 읽기 / 이해 | PDF 추출기 + OCR + 교체 가능한 LLM 어댑터 | 근거가 붙은 JSON 추출 |
| 검색 | 텍스트 검색을 우선 연결, 로컬 임베딩 후보 검색 추가 | 상위 3개 자료와 묶음 반환 |
| 상태 / 예약 | SQLite + 주기적 예약 처리 | 상태 규칙, 중복 방지, 재계획 |
| 화면 | 로컬 자료 카드·묶음·알림·정리 검토 화면 | 원문 보기, 완료·미루기·유지·승인·되돌리기 |
| 실행기 | 허용 경로 안의 파일 이동 | 충돌 방지·해시 검증·복구 |

필수 테이블: `assets`(해시·원본/현재 경로·종류·자료 상태), `extractions`(모델/프롬프트 버전·필드·근거·검토 사유), `bundles` 및 `bundle_assets`, `tasks`(작업 상태·확인된 기한·버전), `user_events`, `reminders`, `action_logs`(승인·이동 전후 경로·해시·실패·undo).

한 파일의 경로는 여러 개일 수 있다. 파일 수정은 기존 추출을 덮어쓰지 않고 새 콘텐츠 버전으로 기록한다. 파일 이동 시 감시기가 발생시킨 이벤트는 실행 이력과 대조해 신규 자료로 중복 등록하지 않는다. 이동은 `planned → moving → verified → committed`로 기록하며, 중단 시 원본·대상 존재와 해시를 검사해 복구한다. 원래 위치가 이미 사용 중이면 되돌리기 때 덮어쓰지 않고 대체 경로를 확인한다.

## 6. 비교할 베이스라인

| 실험 | 동작 | 검증할 점 |
|---|---|---|
| B0 수동 | 사람이 같은 자료를 폴더 정리·검색·알림 등록 | 조작 횟수·찾는 시간의 기준 |
| B1 단순 자동화 | 확장자로 분류, 정규식으로 찾은 첫 날짜에 사전 고정한 규칙으로 알림 | 단순 분류·날짜 감지의 한계 |
| B2 AI 추출 | 같은 LLM으로 분류·기한 추출, 자료별 독립 알림 | 의미 추출의 효과 |
| **B3 제안 베이스라인** | **B2 + 자료 묶음 + 사용자 상태 + 변경 공고 재계획 + 승인 이동·되돌리기** | **중복 알림과 불필요 정리 감소, 실제 재사용 연결** |

B2와 B3는 모델·프롬프트·입력 자료를 동일하게 유지한다. 이후 임베딩 검색 추가 효과는 별도로 비교한다. 이 프로젝트의 첫 목표는 B3를 끝까지 동작시키고 B1·B2와 차이를 측정하는 것이다.

## 7. 데이터·평가 계획

제안: 총 48개 자료(유형별 16개)를 사람이 주석한다. 같은 행사·과제·템플릿의 변형이 양쪽에 섞이지 않도록 개발 24개 / 평가 24개로 그룹 분할한다. 정확한 유형별 비율보다 그룹 분리를 우선한다. 테스트를 보고 규칙을 고치면 새 평가셋이 필요하다.

정답은 종류·목적 후보의 허용 범위·묶음 ID·기한 종류/정규화값·근거·이벤트 후 기대 상태·알림·이동 결정을 포함한다. 파일 정답과 사용자의 신청·완료 사건은 별도로 작성한다. 작은 평가셋의 결과는 탐색적 수치로 보고한다.

- 분류: 정확도와 미분류율을 함께 보고. 확인 요청 후 성능은 최초 자동 성능과 구분.
- 기한: 기한이 없는 자료까지 포함한 정밀도·재현율, 종류·날짜·시간 일치, 근거 일치율.
- 묶음: 잘못 합친 비율과 관련 자료 누락률.
- 검색: 사전 작성한 사용자 질의의 Hit@3와 찾는 시간. UI·시작 조건을 맞춰 비교.
- 알림: 기대 알림 대비 precision/recall, 중복 발송률, 완료 후 불필요 알림 수.
- 정리: 잘못된 제안률, 승인 없는 이동 수, 이동 실패 시 경로 일관성, 되돌리기 성공률.
- 사용성: 파일별 수동 입력·확인·검색 조작 횟수. AI 호출 시간·호출 수·비용도 기록.

필수 시나리오 8개: 정상 저장→알림→완료→보관→되돌리기 / 동일 파일 중복 / 유사하지만 다른 버전 / 모호한 날짜 / 마감 연장과 기존 알림 교체 / 완료·미루기·정리 거절 / 영수증 장기 보관 / 파일 잠김·이름 충돌·이동 중 재시작.

정합성 통과 조건: 승인 없는 이동 0건, 완료 후 활성 행동 알림 0건, 동일 알림 중복 0건, 이동·복구 후 파일 손실 0건, 충돌 없는 정상 되돌리기 전부 성공. 이는 정의한 테스트 범위의 통과 기준이며 아직 측정 결과가 아니다. AI 품질 목표는 개발셋 파일럿 후 평가셋 실행 전에 고정한다.

## 8. 구현 순서와 대표 시연

1. 수집기·해시·SQLite·자료 카드부터 연결한다. 같은 파일 두 번 저장해 중복을 확인한다.
2. PDF/OCR→AI JSON→근거 검증→확인 화면을 연결한다.
3. 자료 묶음·텍스트 검색·상태·예약 취소·변경 공고 갱신을 구현한다.
4. 완료 확인·유형별 정리 제안·승인 이동·실패 복구·되돌리기를 붙인다.
5. 그룹 분할한 고정 평가 자료와 사건 타임라인으로 B1/B2/B3를 비교한다.

대표 시연: 행사 캡처와 신청 PDF 저장 → 한 묶음으로 연결 → 마감 근거를 가진 알림 → 연장 공고 저장으로 예약 교체 → 사용자 신청 완료 → 신청 증빙은 유지, 안내 자료만 정리 제안 → 승인 이동 → 되돌리기. 이 흐름이 첫 완료 기준이다.
