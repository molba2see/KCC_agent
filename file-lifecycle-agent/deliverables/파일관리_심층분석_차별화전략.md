# 파일 관리 에이전트: 선행 구현 심층 검토와 차별화 전략

2026-11-02 · 대상: 앞서 소개한 GitHub 5개와 논문 3편에, 조사 문서의 추가 저장소 1개·논문 1편을 포함한 **저장소 6개·논문 4편**. 경쟁 기능 누락을 줄이기 위해 공식 제품 문서 3개도 보조 확인했다.

**제안 결론: ‘기존 프로젝트 구조와 파일 간 관계를 보존하면서, 자료 유입부터 사용 후 보관까지 이어서 처리하는 에이전트’로 구체화한다.** 내용 분류·개인화·되돌리기·확인 질문 각각은 이미 있다. 차별화의 검증 단위는 **프로젝트와 연결된 파일 묶음의 시간에 따른 정리 결정**이다. 논문 수준 알고리즘 신규성을 확인했다는 뜻은 아니다.

이번에는 저장소를 로컬에 읽기용으로 받아 커밋을 고정하고, 핵심 처리 코드·관련 테스트·논문 방법·평가·한계를 확인했다. 전체 의존 라이브러리나 논문 참고문헌의 모든 줄을 읽은 것은 아니다. 경쟁 프로그램을 실행하거나 같은 데이터로 성능 측정하지 않았다. **확인된 구현 / 확인 범위의 한계 / 우리의 제안**을 구분한다. 재현 가능한 출처 목록은 [심층조사 출처 스냅샷](심층조사_출처_스냅샷.json)에 있다.

## 1. 각 저장소를 읽고 달라진 판단

### 1.1 AI File Sorter — 가장 강하게 비교해야 할 구현

확인: `CategorizationService`, 분류 동작 문서, `UserLearningStore`, `ProtectedProjectDetector`, `UndoManager`, 관련 단위 테스트와 live-LLM 테스트 설명.

- 승인 사례를 별도 SQLite에 기록한다. 파일명·경로·확장자·문맥과 임베딩을 사용해 분류 후보를 검색한다. 단순히 과거 라벨만 캐시하는 구조보다 넓다.
- 프로젝트 루트의 `.git`, `pyproject.toml`, 게임 엔진 표식 등을 검사해 강한 프로젝트 신호가 있으면 재귀 스캔에서 제외한다.
- 복구 계획에는 경로·크기·수정 시각·파일 식별 정보를 남기며, 충돌·변경 시 건너뛰는 검사가 있다. 테스트도 해당 동작을 다룬다.

따라서 **RAG로 개인화, 사용자 수정 반영, 프로젝트 보호, undo**만으로 차별화하기 어렵다. 확인한 보호 경로는 프로젝트 루트를 건드리지 않는 방식이다. 우리가 비교할 가설은 **새로 유입된 자료를 그 프로젝트의 자료 묶음에 연결하고, 필요한 참조를 보존한 채 보관 계획을 만드는 것**이다. 이 기능이 전체 저장소 어디에도 없다고 단정하지 않는다.

### 1.2 Local File Organizer — 이전 설명을 수정해야 하는 부분

확인: `main.py`, `file_utils.py`, 텍스트·이미지 처리, `data_processing_common.py`.

- 본문 요약에서 파일명과 일반적인 주제 폴더명을 생성한다. 텍스트 파일명 프롬프트는 최대 3단어, 폴더명은 최대 2단어를 요구한다.
- **확인한 실행 코드는 원본을 이동·삭제하지 않는다. `os.link()` 또는 `os.symlink()`로 정리된 구조를 만든다.** 이전의 ‘이동 기반 정리’라는 해석은 이 코드 경로에 맞지 않는다.
- 내용 처리 대상 확장자 목록이 정해져 있다. 이름 후처리에는 숫자 제거 등이 있어 버전 정보를 파일명에 유지하려는 경우 별도 검토가 필요하다.

파일의 주제를 잘 요약하는 것과 사용자의 기존 업무 위치를 맞히는 것은 별개다. 비교 실험에서는 원본을 남기는 링크 모드를 우리의 이동 모드와 같은 지표로 평가하지 말고, **정리 뷰 생성 / 실제 원본 정리**로 구분해야 한다. 이 구현을 근거로 ‘원본을 남기는 가상 정리’ 자체를 새로움으로 주장할 수도 없다.

출처: [정리 연산과 링크 실행](https://github.com/QiuYannnn/Local-File-Organizer/blob/a19559942a35d98e9d2168fa58f288d9ea294bc6/data_processing_common.py#L123), [메타데이터 생성](https://github.com/QiuYannnn/Local-File-Organizer/blob/a19559942a35d98e9d2168fa58f288d9ea294bc6/text_data_processing.py#L64), [지원 경로](https://github.com/QiuYannnn/Local-File-Organizer/blob/a19559942a35d98e9d2168fa58f288d9ea294bc6/file_utils.py#L120).

### 1.3 organize — ‘단순 확장자 분류’보다 강한 규칙 기준선

확인: 규칙 문서, 이동·대상 경로 처리, 중복 필터, 폴더 구조 유지·충돌 테스트.

- 위치→필터→행동을 순서대로 실행하는 설정 가능한 엔진이다. 정규식·본문·날짜와 사용자 정의 코드를 조합할 수 있다.
- 원래 상대 경로를 목적지에 반영하는 테스트가 있다. 폴더 구조 보존을 전혀 못 하는 도구라고 비교하면 안 된다.
- 중복 필터는 크기·부분 데이터·해시로 좁히며, 원본 선정 기준도 설정한다. 이름이 같은 파일과 내용이 동일한 파일을 구분한다.

약한 확장자 스크립트만 비교 대상으로 삼으면 기여를 과장하게 된다. 먼저 사용자가 실제로 쓸 만한 규칙을 만들어 비교하고, **최초 규칙 작성 시간과 새 프로젝트에 맞춰 고친 횟수**를 함께 측정한다. 선언된 규칙을 안정적으로 실행하는 능력과 자료 목적·완료 상태를 추정하는 능력은 분리해 평가한다.

### 1.4 pneelamr/ai-file-organizer — 우리 최초 파이프라인과 직접 겹침

129줄의 `organizer.py` 전체를 확인했다. 새 파일 이벤트→1초 대기→PDF/OCR→Ollama→분류 폴더 생성→이동이다. LLM 입력은 파일명과 본문 앞 500자이며, 고정 카테고리 밖 응답·호출 오류는 `Other`로 보낸다. 이동은 직접 `shutil.move()`로 수행한다.

### 1.5 TheYellowDuck/ai-file-organizer — 불확실성 보류도 이미 있음

확인: 계층형 임베딩 분류, LLM 프롬프트·응답 처리, 스캐너·이동기, 이동·종단 테스트.

- 임베딩 경로는 계층별 유사도와 임계값으로 분류한다. LLM 경로는 범주 트리에서 목적지를 선택하고 자기보고 confidence가 낮으면 `Review`로 보낼 수 있다.
- 이동·복사·미리보기·이름 충돌 처리와 이동 후 append/fsync 저널·undo 스크립트가 있다.
- 종단 테스트는 모의 LLM으로 분류→이동→저널→복구를 검사한다. 해당 테스트만으로 실제 의미 분류 정확도나 모든 강제 종료 시점의 복구가 증명되지는 않는다.

**“확신이 없으면 보류” 자체는 차별점이 아니다.** 우리는 자기보고 숫자보다 실제 확인한 근거·후보 충돌·관계 보존 조건을 사용하고, 동일 오류 수준에서 사용자 질문을 줄이는지 측정할 수 있다. 이동 저널도 이미 있는 기본 구성으로 본다.

출처: [LLM confidence와 Review 처리](https://github.com/TheYellowDuck/ai-file-organizer/blob/cf5c57c5ddd7d84493ee097e67d8287173bf63bb/llm/classifier.py#L140), [임베딩 분류](https://github.com/TheYellowDuck/ai-file-organizer/blob/cf5c57c5ddd7d84493ee097e67d8287173bf63bb/classifier/hierarchical.py#L100), [이동·저널](https://github.com/TheYellowDuck/ai-file-organizer/blob/cf5c57c5ddd7d84493ee097e67d8287173bf63bb/organizer/mover.py#L178), [종단 테스트](https://github.com/TheYellowDuck/ai-file-organizer/blob/cf5c57c5ddd7d84493ee097e67d8287173bf63bb/tests/test_e2e.py#L33).

### 1.6 AIOS-LSFS — 의미 연산과 버전 기록 자체를 재발명하지 않기

확인: 논문과 함께 `lsfs.py`, `vector_db.py`, 저장소 테스트 설명.

watchdog 변경 감시, Chroma 인덱스, Redis 버전 기록과 복원 코드가 있다. 확인한 이력 키의 해시는 파일 바이트가 아니라 **경로 문자열**을 대상으로 한다. 이벤트 처리·복원 경로는 파일을 텍스트로 읽고 쓰므로, 모델 가중치 같은 바이너리의 원본 보존에 그대로 적용한다고 가정하면 안 된다.

자연어 검색·변경 요약·버전 복구는 선행 구현이다. 재사용할 개념은 **파일 저장·검색과 자연어 판단의 분리**다. 우리의 제안은 경로와 별개인 자료 ID, 바이트 해시, 업무 관계·보관 정책을 기록하고, 정리 전후 실제 사용자 작업이 유지되는지를 검증하는 쪽이다.

## 2. 논문을 자세히 읽고 적용할 점

### 2.1 Finding and Reminding — 사용자 작업을 방해하는 ‘정리’를 피하기

본문의 사용자 연구·정보 유형·논의를 읽었다. 두 연구의 7명·15명 참여자를 바탕으로 임시·작업·보관 정보와 위치의 기억 단서를 논의한다. 보관할 파일을 선정하는 부담도 다룬다. 오래된 소규모 관찰 연구라 현재 사용자 전체의 선호로 일반화할 수 없다.

**적용 제안:** 파일이 임시 위치에 있다는 이유만으로 불필요하다고 판단하지 않는다. 사용 중 자료를 옮기면 사용자가 기억한 위치와 ‘해야 할 일’ 단서가 사라질 수 있다. 처음에는 관련 자료 뷰를 제공하고 실제 이동은 업무 상태·사용자 기준을 확인한다. 이 상태 구분 자체도 오래된 개념이다.

출처: [원문 §Reminding·§Three Information Types·§Discussion](https://www.ibiblio.org/msmckoy/spring2006/articles/fileOrganizationFromTheDesktop.pdf).

### 2.2 LSFS — 강한 검색 결과를 정리 성능으로 바꾸어 해석하지 않기

아키텍처·API·평가와 관련 부록을 읽었다. 의미 인덱스·CRUD·group/join·자연어 파서·버전 복구를 다룬다. 파서는 API별 30개 샘플로 평가하고, 의미 검색은 10·20·40·120개 파일 조건을 비교한다. 키워드 검색의 강화된 grep 기준선은 표 4에서 F1 1.0을 보이며 LSFS를 앞선다. 실행 전 사용자 승인도 이미 포함한다.

**적용 제안:** 자연어+벡터 검색이 있다는 이유로 연구 차별점을 주장하지 않는다. 데이터가 정적이고 작은 검색 실험의 우수성이 지속적으로 유입되는 파일의 목적지·보관 결정에도 그대로 성립한다고 주장하지 않는다. 검색·정리·복구의 결과 지표를 나눈다.

출처: [논문 §3–5, 특히 §5.1–5.3·표 2·표 4](https://arxiv.org/html/2410.11843v5#S5).

### 2.3 HippoCamp — 근거 연결을 참고하되 이동 평가를 별도로 만들기

자료 구성·태스크·평가·실패 분석·설계 제언과 근거 주석 부록을 확인했다. 100명 이상 인터뷰에서 선별·가공한 파일을 **3개 대표 프로필**로 집계한다. 핵심은 581개 QA에 대한 답변·근거 파일 검색 평가이며, 답변은 LLM judge를 사용한다. 581명이 독립적으로 사용한 정리 도구 실험이 아니다.

구조·시간·첨부·버전 관계가 순수 임베딩에서 손실될 수 있고, 관련 파일을 찾았어도 근거 해석·대상 연결에서 실패한다고 논의한다. 이 자체도 선행 설계 제언이다.

**적용 제안:** 각 정리 제안에 실제 파일·본문 구간과 관계의 근거를 붙인다. 답변 품질은 보조 지표로 두고, 이동 이후 경로·해시·참조·업무 결과를 별도로 자동 검사한다. ‘그래프·근거 검증을 넣었다’만으로 최초라고 주장하지 않는다.

출처: [논문 §3·§4.3·§5.2–5.3·부록 B](https://arxiv.org/html/2604.01221v1).

### 2.4 Filesystem-Based Memory — 보기 좋은 구조와 실제 효용을 분리하기

기억 표현·대조군·평가·성장·도구 영향과 관련 부록을 읽었다. 대화 기억과 ALFWorld 작업 기억을 대상으로, 원문 덤프·폴더 분류·재구성·에이전트 큐레이션을 비교한다. 조직화가 검색 비용에 도움이 되는 조건은 있지만 답변 정확도에서 일관되게 우세한 구조는 없다. 평가 대화 수와 성장 관찰 기간의 제약도 명시한다.

**적용 제안:** 폴더가 예뻐진 정도나 분류 라벨 개수 대신 **찾는 시간·사용자 수정·상태 변화 후 보존 오류**를 측정한다. 원문 변경 없는 뷰/링크 기준선과 물리 이동을 비교한다. 이 연구는 사용자 다운로드 파일 자체에 대한 직접 성능 근거는 아니다.

출처: [논문 §3·§4.2·§4.4–4.5](https://arxiv.org/html/2607.26637v1).

## 3. 추가로 확인한 제품 때문에 제외해야 할 약한 차별점

- **Sparkle:** 최근 자료를 일정 기간 두는 Recents, 수동 라이브러리 존중, 사용자 이동 선택 기억, 이동 기록·복구·중복 표시를 설명한다. ‘최근 파일을 바로 안 옮긴다’만으로는 부족하다. [공식 문서](https://help.makeitsparkle.co/en/articles/13225419-how-sparkle-works)
- **Poly:** 프로젝트 폴더로 이동, 복수 목적지가 애매할 때 질문, 미리보기·정리·중복 확인을 설명한다. ‘프로젝트 분류+확인 질문’도 단독 차별점이 아니다. [공식 문서](https://docs.poly.app/agent/organizing-files)
- **Hazel:** 폴더 감시, 본문·메타데이터·날짜 조건, 이동·압축·휴지통 등의 규칙을 설명한다. ‘오래된 파일을 정리’ 역시 기존 자동화다. [공식 문서](https://www.noodlesoft.com/manual/hazel/hazel-basics/about-folders-rules/)

위 제품은 문서만 확인했으며 내부 알고리즘이나 성능을 검증하지 않았다. 따라서 기능이 없다는 결론을 내리는 자료로 쓰지 않는다.

## 4. 추천하는 차별화 방식

### 4.1 제품 정의

**“다운로드한 자료를 사용자의 실제 작업에 연결하고, 그 작업을 이어가거나 재현하는 데 필요한 관계를 보존하면서 정리하는 에이전트.”**

파일 정리라는 원래 목적을 유지한다. 데이콘은 가능한 시연 하나이며 전체 타겟을 대회로 제한하지 않는다. 일반적인 과제·연구·업무 프로젝트의 문서·이미지·ZIP·결과물에도 적용한다.

성공의 예시는 다음과 같다.

| 유입·변화 | 제안할 행동 | 필요한 근거 |
|---|---|---|
| 이름이 제각각인 안내 PDF·양식·참고 CSV 유입 | 기존 A 프로젝트의 자료 묶음에 연결 | 본문 작업 ID, 기존 README·자료와의 연결 |
| 비슷한 주제의 A·B 프로젝트가 동시에 존재 | 묶음 단위로 한 번 질문하고 귀속 기록 | 구분 가능한 근거 부족을 명시 |
| ZIP과 압축 해제한 폴더가 함께 존재 | 검증된 포함 관계를 표시하고 중복 보관 후보 제시 | ZIP 엔트리·파일 해시 비교; 실행 없이 검사 |
| 최종 결과물이 특정 설정·모델 파일을 참조 | 참조 파일 보존, 관련 파일 함께 찾기 | 매니페스트·설정의 경로·실험 ID 등 확인된 연결 |
| 사용자가 프로젝트 완료를 확인 | 보관 묶음과 보존 대상 제시; 진행 중 공용 자료 유지 | 완료 사건, 보관 정책, 다른 활성 프로젝트의 참조 |

이 관계들을 자동으로 항상 알아낼 수 있다고 가정하지 않는다. 파일 내용만으로 실제 저장 목적을 구분할 수 없는 경우는 남는다.

### 4.2 방법 A: 파일 묶음과 기존 작업을 함께 고려하는 귀속 결정

1. 처음에 감시 폴더와 기존 프로젝트 루트만 등록한다. 자료마다 목적을 입력하게 하지 않는다.
2. 기존 폴더명·README·승인 사례에서 프로젝트 후보를 검색한다. 키워드+임베딩은 후보 축소용이며 그 자체를 기여로 주장하지 않는다.
3. 새 파일의 본문·파일명·구조화 ID와 관련 파일을 확인한다. 가까운 다운로드 시간은 보조 신호로만 사용한다.
4. 동일 ZIP, 문서에 명시된 첨부 ID, 설정의 상대 경로 등 확인된 관계를 우선해 **묶음 단위** 귀속을 결정한다. 내용이 비슷하다는 이유만으로 묶지 않는다.
5. 후보가 충돌하면 대표 질문 한 번으로 여러 파일의 귀속을 확인한다. 이득은 ‘질문 기능’이 아니라 **같은 오류 수준에서 줄어든 질문·수정 횟수**로 입증한다.

자동화 권한과 판단 확신은 분리한다. 사용자가 처음에 허용한 폴더·작업·행동 범위 안에서 검증된 낮은 위험의 분류·태그·자료 뷰 갱신은 자동 수행할 수 있다. 원본 이동도 명시적으로 허용한 범위와 보존 제약을 만족할 때만 자동화하고, 새 목적지·참조 변경·보관 전환처럼 영향이 큰 계획은 묶음 단위로 확인한다. 모든 파일마다 승인받는 도구로 끝나지 않도록 확인 부담을 지표에 포함한다.

### 4.3 방법 B: 관계를 보존하는 실행 계획

SQLite에 `files`, `projects`, `relations`, `events`, `plans`, `actions`를 둔다. 별도 그래프 DB나 GNN부터 도입할 필요는 없다.

관계는 `contains`, `exact_duplicate`, `version_candidate`, `referenced_by`, `produced_by`, `belongs_to` 등으로 기록하되 **확인된 관계 / 추정 관계**를 구분하고 근거를 남긴다. 예컨대 날짜가 비슷하다는 것은 `produced_by`의 확정 근거가 아니다.

LLM은 프로젝트·관계·행동 후보를 제안하고, 코드는 다음 제약을 검사한다.

- 활성 작업에서 참조하는 파일은 정리 대상에서 제외한다.
- 경로 의존성이 있는 묶음의 일부만 이동하지 않는다. 완결된 묶음 전체 이동도 외부 참조가 없거나 별도 확인된 경우만 허용한다.
- 구조를 해석하지 못한 가중치·코드·바이너리는 이름 변경·분해 이동을 보수적으로 제한한다. 가중치를 로드·실행해서 내용을 알아내려 하지 않는다.
- 정확한 복사본과 다른 버전을 구분한다. 수정 시각이 최근이라는 이유만으로 유일한 최종본을 선택하지 않는다.
- 실행 전 해시·경로·참조 상태를 다시 확인하고 실행 이력으로 복구한다.

‘프로젝트를 전부 건너뛰는 보호’와 비교해 **안전하게 연결·정리할 수 있는 파일의 범위가 얼마나 늘어나는가**가 평가할 차이다. 보호 기능 자체의 최초성을 주장하지 않는다.

### 4.4 방법 C: 작업 상태가 바뀔 때 보관을 다시 판단

자료의 종류와 생명주기를 분리한다. 같은 PDF라도 현재 작업의 필수 참고자료인지 완료된 결과물인지에 따라 처리 방침이 달라진다.

파일은 `유입 → 귀속 대기/연결 → 사용 유지 → 보관 검토 → 보관`으로, 프로젝트는 `진행/중단/완료`로 별도 관리한다. 완료는 사용자의 명시적 확인 또는 해당 앱과 연동한 신뢰 가능한 사건으로 기록한다. 파일 열기·경과 시간·마감만으로 완료를 확정하지 않는다.

‘프로젝트 완료’ 한 번의 확인으로 안내·임시 결과·최종 결과·공용 참조 자료를 함께 평가한다. 영구 삭제는 첫 MVP에서 제외하고 보관 이동을 검증한다. 보류·유지 의사는 조건이 달라지기 전 반복 질문하지 않는다.

단순 대기 기간·미사용 기간 정리와 구분되는 가설은 **같은 파일도 연결된 작업과 의존관계가 바뀌면 보존 판단이 달라지는가**다. 실제 사용자 부담 감소가 없으면 이 복잡도를 추가할 근거도 없다.

## 5. ‘새롭다’고 말할 수 있는 수준

| 주장 | 현재 판단 |
|---|---|
| AI가 내용을 읽고 자동 분류한다 | 이미 직접 구현 다수 |
| 로컬 모델·개인화·undo·확인 질문을 넣는다 | 기존 기능. 필수 구성으로 취급 |
| 그래프·RAG·에이전트 프레임워크를 사용한다 | 기술 선택. 그 자체는 차별점 아님 |
| 프로젝트·관계·사용 상태를 함께 보고 정리한다 | 구체화할 제품·실험 방향. 전 세계 최초라고 확정할 근거 없음 |
| 같은 모델·오류 수준에서 확인·수정 비용을 줄이고, 상태 변화 후 필요한 파일 보존률을 높인다 | 우리가 실제로 증명해야 할 기여 |

캡스톤의 제품 차별화는 충분히 검토할 수 있다. 논문 수준의 새로운 알고리즘을 주장하려면 추가 선행연구 검토와 통제된 비교 결과가 필요하다. 넓은 ‘라이프사이클’ 명칭만으로 그 차이가 생기지는 않는다.

## 6. 검증 설계

### 비교 대상

수동 정리, 의미 있는 규칙을 작성한 organize, AI File Sorter, 현재 v2 로컬 프로토타입을 비교한다. Local File Organizer는 원본 보존 링크 기준선으로 별도 다룬다. 외부 도구는 실제 실행 가능한 모델·형식 범위를 맞추고 버전·설정을 고정한다. 지원 밖 파일은 공통 평가와 확장 평가를 나눈다.

알고리즘 효과를 분리하려면 우리 코드 안에서 **동일 추출기·동일 모델·동일 입력**으로 다음 네 조건을 추가한다.

| 조건 | 추가 정보 | 비교할 효과 |
|---|---|---|
| C0 | 파일별 본문·이름 → 폴더 제안 | 기본 내용 분류 |
| C1 | C0 + 기존 프로젝트 후보·승인 사례 | 작업 문맥 |
| C2 | C1 + 확인된 관계·묶음 제약 | 잘못된 분해 이동 감소 |
| C3 | C2 + 프로젝트 상태·보존 정책·확인 이력 | 상태 변화 후 정리 부담 감소 |

경쟁 제품 비교는 제품 전체 차이고, C0–C3는 우리 설계의 각 요소 효과다. 이를 혼동하지 않는다. 단순히 더 좋은 모델을 쓴 결과를 관계·상태 관리 효과로 설명하지 않는다.

### 첫 평가 자료

제안 규모: 3~5개 프로젝트, 혼합 파일 100~150개, 5개 시점의 유입·변경 사건. 자료가 이미 모두 있는 정적 폴더 평가와, 파일 유입→수정→완료→다른 프로젝트 재사용의 순차 평가를 나눈다. 이 수량은 실행 계획이며 확보·실험 완료 수치가 아니다.

포함할 스트레스 사례는 유사 주제의 다른 프로젝트, 동일 이름·다른 내용, 다른 이름·동일 바이트, 버전이 다른 결과물, ZIP 포함 관계, 상대 경로 참조, 여러 프로젝트가 공유하는 파일, 목적 불명 자료다. 파일의 실제 목적지·보존 여부는 사용자 또는 사전 작성한 업무 시나리오로 정답을 정한다. 파일 내용에서 그 사용자 정답을 역으로 생성하지 않는다.

정답은 허용 목적지 집합·그대로 두기·원본 보존 뷰도 포함한다. 하나의 폴더 트리만 정답으로 강제하지 않는다. 모델 개발용과 평가용은 프로젝트·원본·변형 그룹으로 분리한다. 평가셋을 보고 규칙을 고치면 새 평가가 필요하다. 개인화 효과는 새 사용자와 승인 이력이 있는 사용자를 구분한다.

### 핵심 지표와 판정

- **사용자 부담:** 설정 시간 + 질문 응답 시간 + 수정·복구 시간. 클릭 수만 줄이고 사고를 늘리는 방법은 성공으로 보지 않는다.
- **귀속:** 프로젝트/자료 묶음 정확도와 미분류·보류율을 함께 보고한다.
- **안전:** 잘못된 이동, 참조가 깨진 묶음, 필수 보존 파일을 정리 대상으로 제안한 비율. 보존 정밀도·누락과 불필요 보존도 함께 본다.
- **연속성:** 새 자료 유입 후 기존 배치를 불필요하게 바꾼 비율, 완료·재개 후 판단 변경의 정합성.
- **효용:** 사전 정한 실제 파일 찾기·작업 재개·결과 재현 과제의 시간과 성공률.
- **자동화:** 오류 수준별 자동 처리 비율과 확인 질문 수를 함께 비교한다. 모두 보류해 오류만 낮추는 결과를 성공으로 보지 않는다.
- **비용:** 추출·모델·정리·사용자 시간까지 기록한다. 반복 질의의 캐시 조건을 맞춘다.

단기 파일럿은 기능 검증이고 사용자 일반화 증거가 아니다. 후속으로 동의받은 5~8명 정도의 탐색적 사용성 실험을 제안하되, 교차 순서·다른 난도 세트로 학습 효과를 줄인다. 작은 표본에서 유의한 우월성을 성급히 주장하지 않는다.

## 7. 현재 코드에서 바꿀 부분과 구현 순서

현재 v2는 행사명·주최자·기한 중심이며 이 목표에 맞는 실험용 예시에 가깝다. 다음은 아직 구현하지 않은 제안이다.

1. `event_name/organizer`를 범용 `project_candidates`, `purpose`, `role`, `evidence`로 확장한다. 다운로드 폴더·프로젝트 루트 등록을 유지한다.
2. 기존 프로젝트의 읽기 전용 목록과 README·승인 자료를 인덱싱해 후보를 만들고, 복사본·ZIP·명시적 경로 관계를 기록한다.
3. 파일별 직접 이동 대신 **묶음 단위 실행 계획**을 만들고, 경로·해시·확인된 참조·보존 정책을 검증한다.
4. 프로젝트 완료·유지·재개를 한 번 확인하는 UI와 보관 계획을 연결한다. 근거 없는 자동 삭제와 변경 없는 반복 질문은 제외한다.
5. C0–C3 비교와 실제 파일 찾기 과제를 실행한다. 그 뒤에 필요한 모델·임베딩·개인화를 확장한다.

처음부터 그래프 신경망, 모델 파인튜닝, 다중 에이전트, 전 디스크 감시, 웹 크롤링을 도입할 이유는 확인되지 않았다. 필요한 도구는 허용 폴더 감시·문서 읽기·프로젝트 후보 검색·관계 검사·계획 실행·복구다. 크롤링은 원본 웹 문서의 변경을 추적하는 별도 요구가 생길 때 추가한다.

발표 시연은 **섞인 다운로드 자료 → 기존 프로젝트에 묶음 귀속 → 유사 자료의 귀속 확인 → 관계를 보존하는 계획 → 프로젝트 완료 → 필요한 원본·공용 파일은 유지하고 나머지는 보관 → 작업 재개·복구**로 잡는다. 발표 메시지는 ‘AI가 폴더를 예쁘게 정리한다’보다 **‘사용자가 다시 정리하고 찾는 일을 실제로 줄였는가’**에 둔다.
